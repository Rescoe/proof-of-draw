# Plan d'internationalisation FR/EN de Proof-of-Draw

| Champ | Valeur |
|---|---|
| Date | 09/10/2026 |
| Statut | Cadrage uniquement — aucun code i18n livré |
| Langues prévues | Français (`fr`) et anglais (`en`) |
| Estimation | 5 à 8 jours pour une version complète et relue |
| Impact Redis / Neon | Aucun accès supplémentaire attendu |

## 1. État réel au 09/10/2026

Proof-of-Draw est actuellement un site français, pas un site bilingue :

- `app/layout.tsx` déclare `<html lang="fr">` ;
- aucun dictionnaire de traduction n'existe ;
- aucune dépendance ou configuration i18n n'est présente ;
- aucune route localisée `/fr` ou `/en` ;
- aucun sélecteur de langue ;
- aucune détection de `Accept-Language` ;
- navigation, pages, métadonnées, attributs d'accessibilité et messages d'erreur sont majoritairement codés directement en français dans les composants ;
- la page Apprendre et sa feuille de route contiennent un volume important de contenu technique français.

Un navigateur peut proposer sa traduction automatique parce que le document annonce correctement `lang="fr"`. Ce mécanisme reste extérieur à PoD : qualité variable, textes dynamiques parfois oubliés, vocabulaire technique instable, métadonnées et partage social non maîtrisés. Il ne constitue pas une expérience anglaise officielle.

## 2. Objectif produit

Un visiteur anglophone doit pouvoir :

- comprendre la proposition de PoD dès l'accueil ;
- parcourir la galerie et la vue Réseau ;
- installer et appairer un écran ;
- dessiner ou animer sans rencontrer de commande française ;
- consulter son profil et comprendre les erreurs ;
- lire la documentation Apprendre, y compris les limites honnêtes du consensus ;
- partager une URL dont le titre, la description et la langue sont corrects en anglais.

Le français reste une langue de première classe. Aucune langue ne doit être une version simplifiée ou en retard fonctionnel permanent.

## 3. Architecture cible

### 3.1 URLs et sélection

- routes publiques préfixées : `/fr/...` et `/en/...` ;
- `/` détecte la préférence initiale (`Accept-Language`) puis redirige ;
- préférence conservée dans un cookie fonctionnel `pod_locale` ;
- sélecteur `FR · EN` visible dans la navigation et utilisable au clavier ;
- le changement de langue conserve autant que possible la page courante et ses paramètres sûrs ;
- les anciennes URLs sans préfixe redirigent vers leur équivalent localisé pour préserver les liens existants.

Le choix exact de l'outil Next.js (dictionnaires internes ou bibliothèque dédiée compatible avec la version du projet) doit être figé dans un petit lot de fondation. Le contrat fonctionnel ci-dessus ne dépend pas de cette bibliothèque.

### 3.2 Dictionnaires

Organisation conseillée par domaines, avec clés typées :

```text
messages/
  fr/
    common
    home
    gallery
    network
    profile
    draw
    animate
    learn
    errors
  en/
    mêmes domaines et mêmes clés
```

Règles :

- français source et anglais versionné dans Git ;
- aucune traduction à la volée en production ;
- aucune API d'IA ou de traduction appelée par un visiteur ;
- paramètres, pluriels et nombres formatés selon la locale ;
- une clé manquante échoue en test et ne doit pas produire silencieusement une interface mixte ;
- vocabulaire technique centralisé dans un glossaire FR/EN.

### 3.3 Contenus à ne pas traduire automatiquement

- noms d'artistes ;
- titres et textes des œuvres humaines ;
- poèmes, manifestes et œuvres ANA ;
- hashes, identifiants, noms de protocoles, noms de fichiers et extraits de code ;
- journaux série reproduits comme preuves matérielles.

Ces contenus peuvent porter plus tard une langue déclarée et une traduction éditoriale distincte, mais le texte original reste la référence.

### 3.4 API et erreurs

Les routes API ne doivent pas choisir une phrase selon la langue du navigateur. Elles doivent progressivement retourner :

```json
{ "error": { "code": "DEVICE_NOT_PAIRED", "detail": "..." } }
```

- `code` stable et traduit par l'interface ;
- `detail` réservé au diagnostic, non utilisé comme libellé principal ;
- compatibilité temporaire avec les réponses actuelles pendant la migration ;
- aucun changement de contrat firmware sans lot dédié.

### 3.5 SEO et accessibilité

Pour chaque langue :

- `<html lang="fr|en">` exact ;
- titres et descriptions de page traduits ;
- liens alternatifs `hreflang` FR/EN et URL canonique cohérente ;
- Open Graph traduit ;
- `aria-label`, textes alternatifs, annonces d'état et messages de validation traduits ;
- pas de texte essentiel uniquement dessiné dans une image.

## 4. Périmètre de traduction

### Priorité 1 — entrée dans le produit

- navigation et pied de page éventuel ;
- accueil ;
- galerie PoD et galerie ANA ;
- vue Réseau, filtres, infobulles et panneaux ;
- onboarding et appairage ;
- pages d'erreur publiques.

### Priorité 2 — création et gestion

- Pod Studio ;
- atelier d'animation ;
- envoi vers un écran ;
- profil et réglages des appareils ;
- confirmations, avertissements et états de chargement.

### Priorité 3 — documentation

- page Apprendre et ses parcours ;
- guides de câblage et d'installation Arduino ;
- synthèse technique ;
- feuille de route et statuts matériels ;
- terminologie de consensus, validation, vote et preuve.

Les affirmations techniques doivent rester strictement équivalentes dans les deux langues. Une traduction anglaise ne doit jamais renforcer une garantie que la version française présente comme expérimentale.

## 5. Lots de réalisation

### I18N-0 — inventaire et glossaire (0,5 jour)

- inventorier les chaînes visibles, métadonnées et réponses API ;
- classer : interface, contenu éditorial, diagnostic, contenu utilisateur ;
- geler le glossaire initial (`drawing`, `artwork`, `display`, `device`, `validator`, `vote`, `block`, `render`, `frame`, etc.) ;
- définir les clés et la règle de repli.

### I18N-1 — fondation technique (0,5 à 1 jour)

- segment de locale ;
- détection initiale et cookie ;
- sélecteur FR/EN ;
- dictionnaires typés et test d'égalité des clés ;
- métadonnées localisées ;
- redirections compatibles avec les anciennes URLs.

### I18N-2 — pages publiques essentielles (1 à 1,5 jour)

- accueil, navigation, galeries, réseau, onboarding ;
- accessibilité et états vides ;
- première relecture anglaise.

Une version anglaise publiable mais encore incomplète peut être atteinte ici, en environ 2 à 3 jours cumulés.

### I18N-3 — création et profil (1 à 1,5 jour)

- dessin, animation, envoi, profil ;
- erreurs fonctionnelles et confirmations ;
- vérification mobile.

### I18N-4 — Apprendre et documentation experte (2 à 3 jours)

- traduction éditoriale complète ;
- relecture du vocabulaire matériel et cryptographique ;
- parité de la feuille de route ;
- exemples et logs laissés intacts mais expliqués dans la langue de la page.

### I18N-5 — QA, SEO et finition (1 jour)

- parcours complets FR et EN ;
- recherche de chaînes françaises résiduelles ;
- vérification des métadonnées, `lang`, `hreflang`, liens et partage ;
- tests clavier, lecteur d'écran et petit écran ;
- vérification qu'aucune route localisée n'ajoute de lecture Redis/Neon.

## 6. Estimation

| Niveau | Délai estimé | Résultat |
|---|---:|---|
| Démonstrateur | 1 à 2 jours | Accueil et navigation traduits, architecture encore partielle |
| Anglais utilisable | 2 à 3 jours | Parcours public principal disponible, documentation experte partiellement française |
| Version professionnelle complète | 5 à 8 jours | Interface, Apprendre, SEO, accessibilité et erreurs cohérents |
| Avec relecture humaine confortable | 1 à 2 semaines calendaires | Temps de relecture, retours et correction du ton inclus |

Cette estimation suppose une migration progressive, assistée pour l'extraction des textes, puis relue humainement. Elle n'inclut pas la traduction éditoriale des œuvres elles-mêmes.

## 7. Tests et critères d'acceptation

- chaque locale contient exactement les mêmes clés ;
- aucune clé brute n'est visible dans le navigateur ;
- aucune page essentielle ne mélange français et anglais ;
- chaque route publique principale existe en FR et EN ;
- `lang`, titre, description et alternates correspondent à la locale ;
- le changement de langue conserve la route et les paramètres autorisés ;
- textes dynamiques, modales, toasts, formulaires et erreurs couverts ;
- dates, nombres et pluriels formatés selon la langue ;
- contenu utilisateur inchangé ;
- TypeScript, tests et build passent ;
- coût Redis et Neon identique avant/après sur les parcours équivalents.

## 8. Garde-fous projet

- ne pas démarrer ce chantier au milieu d'un lot firmware actif touchant les mêmes pages de documentation ;
- ne pas traduire à la volée avec un service externe ;
- ne pas stocker les dictionnaires dans Redis ou Neon ;
- ne pas dupliquer les composants par langue ;
- ne pas modifier les protocoles firmware pour traduire l'interface web ;
- ne pas traduire les identifiants de protocole ou les preuves brutes ;
- préserver les limites et formulations prudentes du consensus ;
- livrer par lots réversibles, avec français inchangé visuellement au premier lot.

## 9. Ordre recommandé dans la feuille de route globale

Le chantier n'est pas urgent pendant le canari matériel actuel. Ordre recommandé :

1. stabiliser le rendu v1 et les piles UNO R4 ;
2. terminer le canari et documenter son verdict ;
3. geler un point de reprise propre ;
4. réaliser I18N-0 et I18N-1 ;
5. livrer progressivement les pages publiques, puis les outils de création et enfin Apprendre.

L'internationalisation est indépendante de l'OTA et n'ajoute aucune charge Upstash Redis ou Neon. Elle peut donc devenir le chantier produit suivant sans remettre en cause les budgets immuables du réseau.
